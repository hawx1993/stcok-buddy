# 修改范围规则

目标：让 Bug 修复只触碰根因和直接验证，不扩大为重构或功能改造。

## 默认边界

默认允许修改：

- 根因所在文件。
- 根因的直接调用方或直接被调用方。
- 与根因同一路径的类型定义、schema、常量或错误处理。
- 覆盖该 bug 的最近测试、selfcheck 或 fixture。
- 必须同步的文档化测试命令或脚本。

默认不允许修改：

- 与复现路径无关的 UI、样式、文案、依赖、构建配置。
- 大范围格式化、目录整理、命名统一、抽象重构。
- 删除业务逻辑、删除 Hook、删除 effect 依赖、删除校验。
- 关闭或降低 TypeScript、lint、test、build 检查。
- 新增 mock/fake/demo/sample/preview 行情数据掩盖问题。

## 文件数量预算

- 默认修改文件不超过 3 个。
- 修改 4~5 个文件时，必须先写明为什么每个文件都与根因直接相关。
- 预计修改超过 5 个文件时，必须停止并向用户确认修改范围。
- 如果修复需要架构改动、依赖升级或迁移，先给方案，不直接执行。

## 上下文预算

- 初始搜索最多 20 个结果。
- 首轮读取最多 5 个文件。
- 调用链最多向上 3 层、向下 3 层。
- 大文件只读相关函数、类型、测试片段。
- 每次扩大上下文前，说明缺少哪条调用链证据。

## 边界确认问题

编辑前回答：

1. 根因文件是哪一个？
2. 哪些文件是直接调用方或直接测试？
3. 是否需要修改 public API 类型？影响谁？
4. 是否有无关格式化或重构风险？
5. 是否有数据、性能、状态同步或兼容性风险？

答案不清楚时，继续定位，不要编辑。

## Diff 纪律

提交前检查：

- `git diff --check` 没有空白或冲突标记问题。
- `git diff` 中每个 hunk 都能对应到根因、测试或验证脚本。
- 没有把旧问题扩大成新功能或新抽象。
- 没有修改用户未要求的功能表现。
- 没有新增生产路径 mock、fake、fallback 行情数据。

## 范围扩大协议

只有出现以下情况才允许扩大范围：

- 根因在共享类型或共享 provider，必须同步调用方。
- 原 bug 的最小复现横跨 UI、IPC、service、provider。
- 测试暴露同一根因在多个入口复现。
- 编译证明 API 变更必须同步。

扩大范围时先说明：新增文件、原因、风险、验证命令。超过 5 个文件必须等待用户确认。
