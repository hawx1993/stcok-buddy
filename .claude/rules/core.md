# Core Development Rules

适用于所有 StockBuddy 开发任务。这里存放长期稳定的通用工程约束；领域细节放在对应 rules、knowledge 或 recipes。

## 基本原则

- 先定位既有边界，再修改代码。
- 优先复用已有 service、provider、hook、组件、类型、测试和已安装依赖。
- 使用能完成需求的最小改动；保持现有业务逻辑、公共 API 和架构边界稳定。
- 修改必须可验证；无法验证时如实说明原因、替代检查和剩余风险。
- 代码风格跟随所在文件的命名、注释密度、拆分方式和错误处理方式。

## 上下文预算

初始阶段保持紧凑：

- 搜索结果最多选 20 个候选。
- 首轮最多读取 5 个代码文件。
- 优先读取相关函数、类型、测试片段；大文件只读必要范围。
- 沿调用链继续读取：Search → Narrow → Read → Trace。
- 每扩展一轮上下文，先明确缺少哪条证据。

需要跨多个领域时，先读 `.claude/knowledge/index.md`，再只加载命中的 Knowledge 和 Recipe。

## 修改边界

默认修改文件不超过 5 个，并且只包含：

- 当前需求的直接实现点。
- 直接调用方或共享类型。
- 直接相关测试或 selfcheck。
- 必要的相邻文档更新。

如果需要修改公共 API、依赖、配置、schema、数据库结构或超过 5 个文件，先暂停并说明：原因、影响范围、可选方案和验证成本。

## 精准修改

- 保持需求之外的功能、文案、颜色、样式、数据流和目录结构不变。
- 不做顺手重构、格式化全文件、依赖升级、目录搬迁或风格统一。
- 不通过删除业务逻辑、降低类型安全、关闭检查或吞掉错误来完成任务。
- 对外部服务、数据删除、存储清理、发布、推送等难回滚操作，先取得用户确认。

## 验证要求

完成后至少考虑：

```bash
pnpm run typecheck
git diff --check
```

再按影响范围选择定向测试、自检或 build。报告必须区分：已通过、失败、未运行及原因。
